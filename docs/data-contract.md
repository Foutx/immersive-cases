# Контракт данных 1.0

Граница: сборщик → импорт → PostgreSQL → API сайта. Схема описывает вход импорта, не ORM и не публичный ответ сайта. Исходные модели stages/models.py и JSON-экспорт не меняются. Адаптер contracts.events.from_pipeline принимает валидированную RawCandidate, EnrichedCase или ScoredCase. Старая культурная база cases.json не является входом этого адаптера.

## Формат пакета

schema_version: строго 1.0. producer: постоянное имя сборщика. collected_at: время формирования пакета с часовым поясом, рекомендуется UTC. events: до 1000 карточек, пустой пакет допустим. Неизвестные поля отвергаются. Несовместимые изменения требуют новой версии. Больший запуск делится на пакеты.

Модель: contracts/events.py. Машиночитаемая схема: docs/event-import.schema.json. Вымышленный пример: docs/event-import.example.json. Проверка: `python -m contracts.validate docs/event-import.example.json`.

## Поля карточки

Обязательны source_record_id, title, description, source_url, proofs (минимум один источник, включая source_url). Строки не должны быть пустыми. Отсутствующие скалярные сведения передаются как null, коллекции как []. Не использовать «неизвестно», 0, фиктивный город или 1 января вместо неизвестной даты.

- start_date/end_date: точные календарные даты ISO YYYY-MM-DD, null при отсутствии. Конец не раньше начала. reported_year хранит отдельно известный год и не превращается в точную дату. Многолетние события допустимы.
- country_code: ISO 3166-1 alpha-2, city, venue: отдельные поля. Код проверяется синтаксически; справочник стран проверит сервис импорта. location_text сохраняет исходное место, если надёжно разделить его нельзя.
- organizers и studios: отдельные списки названий. client_name: заказчик, не организатор по умолчанию.
- category и format_text: исходная категория и описание формата.
- tags: kind=format/technology и стабильный slug. Сервис будет хранить уникальную пару (kind, slug). Русские подписи принадлежат справочнику сайта.
- occurrence: unknown/announced/ongoing/completed. Это сообщение сборщика, не статус модерации.
- score и score_method передаются вместе либо оба null. Диапазон 0–100; это рейтинг конкретного алгоритма, не доказанная степень иммерсивности.

## Доказательства и иммерсивность

proofs содержит уникальные URL и тип official/article/video/photo/other. Доступность: checked_at (с часовым поясом), http_status, error. Если проверки не было, значения null. Таймаут не равен 404. Ответ 200 не доказывает реальность события и может быть страницей блокировки. HTTP-проверка должна впоследствии выполняться защищённым сборщиком, с запретом внутренних адресов и проверкой перенаправлений; сама схема не разрешает сетевые запросы.

relevance: unreviewed/automatic_match. Ни HTTP 200, ни прежнее video.verified не означают ручную проверку.

claims: конкретное утверждение field + value + evidence (одна или более ссылок с цитатами). field: environment, visitor_actions, system_response, visitor_role, immersion_mechanism, dates, location, occurred. Все ссылки evidence должны присутствовать в proofs.

system_response: reacts/does_not_react. visitor_role: observer/participant/co_creator. Прочие value являются короткими текстовыми утверждениями. Если утверждений нет, признак неизвестен. Для отрицательного утверждения также нужна цитата. Утверждения о разных зонах/режимах допустимы: контекст должен быть указан в цитате. Конфликты отправляются на проверку, а не разрешаются автоматически.

completed требует утверждение occurred с источником. Если end_date известна, она должна быть раньше даты collected_at. При неизвестном окончании ретроспективная публикация может подтверждать проведение: нужна ручная проверка. Дата анонса, год в названии и прошедший календарный срок сами по себе не доказывают проведение. Схема проверяет связи и формат, а не истинность цитаты.

## Идентичность и обновления (для реализации в БД)

База присваивает внутренний UUID. Уникальная внешняя ссылка: (producer, source_record_id), хранится отдельно от events. Перенос события между городами и повторный показ могут быть разными событиями. Название и старый case_id не являются глобальным ключом. Текущий case_id зависит от бренда, названия и года; после изменения этих сведений требуется сверка, а не слепое создание новой карточки.

Повторная загрузка внешнего ключа обновляет запись транзакционно. null и [] не удаляют ранее известные сведения. Подтверждения и теги дополняются с устранением повторов. Ручные исправления не перезаписываются парсером. Для явного удаления позднее нужен отдельный административный механизм. Совпадение URL и похожее название дают кандидатов на объединение, но не достаточны для автоматической склейки.

## Приём и публикация

Корректный импорт поступает в draft. Статусы draft/in_review/published/rejected, reviewer и внутренний UUID управляются backend; передавать их в этом контракте нельзя. Импорт не равен публикации.

Минимальная политика публикации для первой версии: подтверждённое проведение; объяснение механизма иммерсивности с источником; проверенный первоисточник плюс релевантное медиа или независимая статья; отсутствие неразрешённых конфликтов; решение модератора. Наличие видео не обязательно для хранения черновика. Отбор по этим правилам будет реализован в сервисе, не в текущем контракте. Сайт видит только published.

Проверки ссылок должны обновляться отдельно от модерации. Политика давности проверки будет конфигурацией backend. collected_at не подменяет дату последнего успешного сбора: последняя берётся из журнала запусков.

## Совместимость со сборщиком

Адаптер сохраняет исходное место без угадывания страны/города. brand_or_client → client_name, production_agencies → studios. source_url и discovered_from имеют тип other, пока роль источника не установлена. video.verified → automatic_match; время и HTTP-статус не выдумываются. Год не становится датами, occurrence остаётся unknown. Технологические маркеры не становятся доказанными claims. Сведения enrich/scoring нужно передавать до to_final, который теряет часть якорей.

## Границы текущей работы

Реализованы контракт, адаптер, JSON Schema, пример, валидатор и тесты. PostgreSQL, миграции, upsert, модерация, HTTP-проверка и API относятся к следующим пунктам. Контракт выбран для интеграции, но не выдаётся за согласованный другой командой.
