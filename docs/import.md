# Импорт результатов сборщика

Сервис принимает JSON-пакет версии 1.0 из docs/data-contract.md. Источником может быть LLM-парсер, API, ручная подборка или несколько сборщиков. На этом этапе сервис не обходит сайты и не вызывает LLM.

## Запуск

```powershell
python -m services.import_events path/to/batch.json
```

База по умолчанию: data/immersive_cases.sqlite3. Миграции применяются автоматически. Для демонстрационного примера используйте отдельный файл:

```powershell
python -m services.import_events docs/event-import.example.json --db data/demo.sqlite3
```

Пример вымышленный, не является реальным событием. Повторный запуск должен показать added=0, unchanged=1. Не загружайте этот пример в рабочую подборку.

Результат команды: run_id, added, updated, unchanged, stale, conflicts. conflicts считает расхождения в основных полях, а не автоматически решённые конфликты. Успешный импорт не означает проверку достоверности или публикацию.

## Правила

- Идентичность: producer + source_record_id. Внутренний UUID создаётся один раз. Для одного сборщика producer сохраняется постоянным между запусками, источники сайтов отражаются в source_url/proofs.
- Разные внешние ключи, даже с одинаковым названием, не склеиваются. Сервис дедупликации или модератор позже сможет связать их с одним event_id. Возможность таблицы event_sources поддерживает несколько внешних ключей одного события, но API такой привязки пока не реализован.
- Основные заполненные поля сохраняются. Пустые поля дополняются только у непроверенного draft. При расхождении входное значение и имя поля сохраняются в import_records для разбора. Автоматического исправления уже заполненного значения нет, даже если оно получено ранее парсером.
- null и [] ничего не удаляют. Теги, участники, подтверждения, утверждения и цитаты добавляются без повторов. Разные утверждения сохраняются, включая противоречащие друг другу; сервис не определяет их истинность.
- Статус модерации и ручные отметки не меняются. Для уже проверенных источников тип, заголовок и релевантность сохраняются. Проверка доступности URL обновляется только по более новому checked_at, независимо от ручной оценки содержания.
- Более старый collected_at для известного внешнего ключа даёт stale: карточка не меняется. Одинаковое время допускается для повторной отправки или дополнения. Время нормализуется в UTC.
- Пакет валидируется целиком до записи. Ошибка контракта прекращает импорт без изменения БД и выводится в консоль. Такие ошибки до начала запуска не записываются в import_runs.
- После валидации запуск записывается в журнал. Изменения карточек и import_records выполняются одной транзакцией BEGIN IMMEDIATE. Ошибка записи откатывает весь пакет и оставляет failed в журнале. Аварийное завершение процесса может оставить running; автоматического восстановления зависших запусков пока нет.
- Каждый запуск сохраняет входной JSON и конфликтующие имена полей в import_records. Эти данные нужны для разбора и будущей модерации. Политика очистки истории пока не задана.
- При импорте ссылки не открываются: сервис сохраняет переданные результаты проверок. HTTP 200 или automatic_match не означают ручную проверку.

## Подключение будущего парсера

Готовый парсер формирует пакет ImportBatch и вызывает services.import_events.import_batch(payload), либо сохраняет JSON для команды выше. Для существующих валидированных карточек сборщика есть contracts.events.from_pipeline(case). Вызов из stage4 подключён флагом --save-db; отдельный import-db принимает сохранённые карточки.

Нужен стабильный source_record_id: старый case_id зависит от названия/бренда/года. Изменение такого ID потребует сопоставления, иначе получится отдельная карточка. Не используйте название или URL каталога как единственный идентификатор разных показов.

## Проверка

`python -m unittest discover -s tests -p "test_*.py"`

Проверены повторный импорт, дополнение связей, сохранение ручных значений, разные producer, устаревшие пакеты, свежесть проверки ссылок, откат пакета и отказ в приёме невалидных данных. Эти тесты не проверяют качество внешнего LLM-парсера.

## Интеграция с существующим сборщиком

Команды выполняются из корня проекта:

```powershell
# Сохранённые карточки второго этапа, без повторного LLM и поиска видео
python immersive_pipeline/main.py import-db --input immersive_pipeline/data/enriched_cases.json

# Черновики первого этапа также поддерживаются, даже без видео
python immersive_pipeline/main.py import-db --input immersive_pipeline/data/raw_candidates.json

# Обычный JSON-экспорт и дополнительная запись в SQLite
python immersive_pipeline/main.py stage4 --save-db

# Полный сбор с сохранением результата в SQLite (требует настроенных API)
python immersive_pipeline/main.py all --save-db
```

Для отдельной тестовой базы добавьте `--db-path data/demo.sqlite3`. Команды работают и через run.ps1 при установленных зависимостях в выбранном им Python.

import-db поддерживает raw_candidates, enriched_cases, scored_cases и top_cases. Культурный cases.json и final_cases с video_urls не принимаются: финальный экспорт теряет якоря и подробные подтверждения. Для импорта готового контрактного пакета используйте прежнюю команду services.import_events, а не import-db.

producer всегда immersive_pipeline, чтобы одна карточка разных этапов не становилась разными записями. Идентификатор берётся из валидированной карточки. Для сохранённого файла collected_at пакета берётся из времени изменения файла как признак порядка снимков. Это не подтверждённая дата последнего сбора. Перенос файла может поменять это время; при необходимости точного управления формируйте контрактный пакет с явным collected_at.

stage4 --save-db сохраняет в SQLite только принятые итоговым экспортом карточки, используя полную ScoredCase до сокращения в FinalCase. Условия этапа 4 (видео, strict, publish) сохраняются. Для черновиков и неполных наборов без видео используйте import-db. Все импортированные события остаются draft; автоматической публикации нет.

Без --save-db этап 4 по-прежнему пишет только JSON. В режиме --save-db невалидная карточка прерывает весь экспорт до записи JSON/БД. Отсутствующий входной файл вызывает ошибку, а не успешный пустой импорт. Лимит пакета остаётся 1000 карточек: большие наборы нужно разделять.

JSON и SQLite не являются общей транзакцией: сначала сохраняется JSON, затем выполняется транзакционный импорт. При ошибке БД JSON остаётся на диске; команда сообщает об ошибке и возвращает ненулевой код. Для повторной попытки используйте import-db с исходным top_cases.json, не final_cases.json. Успешная запись JSON сама по себе не означает успех записи в БД.

Проверено 37 офлайн-тестов в tests/, включая CLI из другой рабочей папки, повторный импорт, сохранение якорей и JSON-экспорт без обращения к БД. Проверки сетевого LLM, сайтов и поисковых API этим запуском не выполнялись.
